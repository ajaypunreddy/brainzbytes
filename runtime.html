See it run

Three outcomes. One governed execution pattern.

These illustrative journeys make the architecture concrete. Exact connectors and side effects depend on the admitted capabilities in a customer deployment.

Illustrative

Investigate a production regression

An SRE asks for an evidence-backed assessment without giving an Agent unrestricted production authority.

  1. Intent“Explain the error spike after the latest release and prepare the safest next action.”
  2. AdmitResolve the incident, telemetry, repository, release, and runbook capabilities allowed for this operator.
  3. Dry runShow proposed queries, data scopes, parallel investigations, budgets, and any action that would need approval.
  4. AuthorizePolicy permits read-only investigation and draft preparation; rollback or incident acknowledgment remains human-controlled.
  5. ExecuteAgents inspect logs, traces, recent changes, and known patterns in parallel while durable state preserves progress.
  6. ProveReturn the diagnosis, confidence, citations, tool receipts, policy decisions, and a separately reviewable remediation plan.
Illustrative

Prepare a customer renewal brief

An account team needs a current, source-backed view without mixing customer data or sending unreviewed communication.

  1. Intent“Prepare the renewal brief, identify open commitments, and draft the customer follow-up.”
  2. AdmitResolve approved CRM, support, contract, product, and document sources for the user, account, and purpose.
  3. Dry runPreview the fields to retrieve, the comparison logic, and the proposed communication before protected work begins.
  4. AuthorizePolicy filters account data, excludes unrelated customers, and requires an account owner to approve external communication.
  5. ExecuteWorkers assemble history, commitments, risks, usage evidence, and recommended actions into a typed brief.
  6. ProveDeliver citations, freshness, missing-data warnings, approval state, and a draft that cannot be sent autonomously.
Profile-dependent

Coordinate a policy-compliant trip

A traveler wants an itinerary assembled across providers while retaining explicit approval for booking and payment.

  1. Intent“Plan the trip within company policy, compare practical options, and prepare it for approval.”
  2. AdmitResolve travel policy, calendar, approved search providers, expense limits, identity, and regional constraints.
  3. Dry runPresent candidate providers, data shared with each one, estimated cost, timing, and proposed booking actions.
  4. AuthorizePolicy removes disallowed options and requires the traveler or delegated approver before any external commitment.
  5. ExecuteSearch tasks run in parallel; a Workflow joins the results, applies preferences, and pauses durably for approval.
  6. ProveReturn the itinerary, comparison evidence, approval record, and provider receipts when configured connectors perform a booking.

Plain-language model

A relay race with signed handoffs.

A Workflow is not one Agent improvising from start to finish. Each specialist receives only the baton it needs, passes a typed result to the next stage, and records the handoff. Checkpoints let the race pause for approval or resume with another worker after failure.

Run lifecycle

The simple view of a rigorous execution model.

The full design contains more granular authorization, retrieval, binding, checkpoint, disclosure, and audit states; users see a comprehensible progression.

Receive and scrutinize intent

Resolve identity, tenant, roles, relationships, device, purpose, risk, classification, entities, ambiguity, and candidate outcomes.

Resolve the Solution action

Map the selected experience action to an approved Service, ask a clarifying question, or propose a graph from only admitted capabilities and control nodes.

Compile and authorize the complete graph

Validate schemas, field bindings, dependencies, fallback sets, budgets, RAG scopes, model envelopes, tool risk, and approvals.

Freeze the immutable plan

Pin exact Service, Workflow, Agent, MCP, model, policy, schema, source, index, and configuration versions.

Commit the durable run

Persist state, the plan, first tasks or approval request, and transactional outbox before returning acceptance.

Execute typed work

Dispatch through persistent commands; run ready Agents in parallel; use bounded context; checkpoint accepted artifacts.

Invoke tools under delegated authority

The MCP gateway validates the exact call, performs just-in-time token exchange, keeps credentials outside the Agent, and records receipts.

Finalize, disclose, and prove

Validate one canonical result, apply disclosure policy and approval, render approved formats, persist evidence, and reauthorize delivery.

Resilience by design

Long-running work can wait, retry, resume, and compensate.

Durability is a product contract rather than a best-effort property hidden inside an Agent loop.

Durable waits

Release compute while waiting

Human approval, timer, callback, or external event state is persisted. The run resumes from authoritative state rather than holding an open process.

At-least-once safety

Replay without repeating side effects

Inbox/outbox, leases, idempotency keys, accepted artifact hashes, and provider receipts let another worker safely continue after failure.

Saga compensation

Handle partial business failure

Each side effect declares whether and how it can be compensated. Failed plans reverse approved actions or escalate explicit non-compensable state.
